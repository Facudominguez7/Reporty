Cómo viaja cada solicitud

Camino A · autenticación

Ingreso, registro y recuperación

01 / PERSONA

Completa el formulario y recibe un token del widget.

02 / APP

La operación envía el token en captchaToken.

03 / SUPABASE AUTH

Supabase verifica el CAPTCHA cuando está habilitado.

04 / RESULTADO

Se renueva el token consumido; el error permite reintentar.

Camino B · publicación

Crear un reporte o comentario

01 / FORMULARIO

El widget entrega un token asociado a la acción.

02 / SERVER ACTION

Se comprueban sesión, permisos y política CAPTCHA.

03 / SITEVERIFY

Reporty envía token y secreto a Cloudflare y valida la respuesta.

04 / WORKFLOW

Solo si pasa: continúa el proceso de publicación y sus controles existentes.

Acciones: crear_reporte y comentar_reporte. La verificación del reporte ocurre antes del claim de envío y del trabajo de imágenes.

Caso especial · invitado

Dos operaciones, dos tokens

Primero, Supabase consume un token para crear la sesión anónima. Después, Reporty solicita otro para verificar la creación del reporte. No se reutiliza el primero.

Las capas que siguen protegiendo

Siteverify

Exige éxito, hostname permitido y action esperada; rechaza errores de red y respuestas inválidas. Timeout: 10 segundos.

Llaves y entorno

La site key es pública. El secreto permanece en servidor. Producción falla cerrada si falta configuración y rechaza secretos de prueba.

Controles existentes

Permisos, RLS, límites, identificadores de envío, idempotencia y moderación siguen siendo independientes del CAPTCHA.

Fuera de producción, si no hay site key, el guard permite trabajar sin CAPTCHA. El endpoint falso de pruebas se limita a loopback; en producción solo se admite con hostnames permitidos loopback.

Fuera del alcance deliberadamente

Navegación pública, votos, Google OAuth, vinculación de correo de invitados y operaciones administrativas no agregan un challenge nuevo.
